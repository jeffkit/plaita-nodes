## §1 A2R7-08 · 默认 cwd 与显式 repo 同构

基线 `AgentRunNode(repo=None)` 的直跑分支写成 `if repo:`，整块跳过
`preflight_workspace` 与 `run_lock_key`（r7 探针：`preflight_calls=0
run_lock_key=None cwd=None`）。节点文档把「默认进程 cwd」列为受支持模式，
所以本批选择**补齐同构守卫**而不是拒绝无 repo 用法——后者会破坏既有 flow。

修法（`agent_run.py`）：

1. `workspace = str(repo) if repo else os.getcwd()`；
2. 无条件 `preflight_workspace(workspace, run_key=execution_id)`——默认 cwd
   的孤儿 agent 与显式 repo 一样走 kill-before-start；
3. `run_lock_key = _run_lock_key(workspace, run_scope)` 始终传给
   agentproc（spawn 侧遗言落盘，下一次 preflight 可见）；
4. `RunOptions.cwd=workspace`：锁键与实际工作目录不会漂移（repo 缺省时
   等价于继承进程 cwd 的历史语义）。

`run_scope` 仍是每 dispatch 唯一的 `execution_id`（同 `_execute_sandboxed`），
同 cwd 的兄弟 run 互不清锁；无 `execution_id` 的旧执行桩回退裸 workspace 键。

证据（`data/39-probe-repo-none-lock.txt`）：

```
[repo-none] preflight_calls= 1 run_lock_key= /Users/kong/projects/infra4agent/plaita-nodes cwd= /Users/kong/projects/infra4agent/plaita-nodes out= OK
```

回归：`test_repo_none_uses_cwd_for_preflight_and_lock`（调用参数与
`RunOptions` 断言）、`test_repo_none_kills_orphan_in_cwd`（真实 live
孤儿 + 死 spawner 锁 → preflight 击杀、锁文件清理）。

## §2 A2R7-06 · HTTP 200 + 业务错误码判失败

r7 四通道探针：Feishu `code=19003`、WeCom `errcode=93000`、Slack
`ok=false`、DingTalk `errcode=310000` 在 HTTP 200 下全部返回
`{"status": 200, ...}` 成功，通知静默丢失且不触发 `retryTimes`。

修法（`notify_backends.py`）：

| 通道 | 成功判定 | 失败字段 | 可重试业务码（限流族） |
|---|---|---|---|
| Feishu | `code == 0`（缺失视为兼容） | `code` | 9499 / 11232 |
| WeCom | `errcode == 0`（缺失视为兼容） | `errcode` | 45009 / 45033 |
| DingTalk | `errcode == 0`（缺失视为兼容） | `errcode` | 130101 |
| Slack | `ok != false`；纯文本 `ok` 不变 | `ok=false` + `error` | `rate_limited` / `ratelimited` |

- 确定性业务错误 → `WebhookBusinessError(DeterministicRuntimeError)`：
  同时是 `RuntimeError`/`ValueError`，引擎按确定性分类**不重试**，避免凭据
  错误被 `retryTimes` 放大成重复群消息；
- 限流业务码 → `WebhookTransientBusinessError(RuntimeError)`：保留退避重试；
- 错误文案带通道与业务码，并过 `_scrub_url_text` + 200 字符截断（响应体
  可能回显 webhook URL/凭据，延续 A2R8-01 纪律）；
- 字段缺失（既有测试桩/网关只回 `{"ok": true}`）保持成功，输出形状不变。

修复后探针（`data/39-probe-notify-codes.txt`）：

```
[feishu_webhook] raised WebhookBusinessError: feishu_webhook webhook 业务错误 code=19003: invalid webhook token
[wecom_webhook] raised WebhookBusinessError: wecom_webhook webhook 业务错误 code=93000: invalid webhook url
[slack_webhook] raised WebhookBusinessError: slack_webhook webhook 业务错误 code=invalid_token: invalid_token
[dingtalk_webhook] raised WebhookBusinessError: dingtalk_webhook webhook 业务错误 code=310000: sign not match
[http-400] raised DeterministicRuntimeError: webhook 调用失败 HTTP 400: {'msg': 'bad'}
```

回归覆盖：四通道错误码/成功码、Slack 纯文本、错误文案打码、限流码可重试、
真实 Flow 下 `19003` 只发 1 次、`9499` 首发+2 重试共 3 次。

## §3 A2R7-07 · SQL 超时中断查询并归还连接

引擎在节点预算超时时只置位 `execution.cancel_event` 并遗弃线程
（`plaita/core/runner.py::_run_sync_node`）。基线 `sql_query` 不消费该标志：
阻塞的 `conn.execute` 继续跑，`engine.begin()` 的连接一直 checked out 到查询
自然结束（r7 探针：flow 返回后线程仍活、`checkedout=1`）。

修法（`database.py`）：

1. 进入 `engine.begin()` 后启动 daemon 看门狗（仅当执行上下文带
   `cancel_event`/`cancel_requested`，旧执行桩零线程开销），每
   `CANCEL_POLL_SECONDS`（0.25s）检查一次；
2. 取消命中 → `_interrupt_db_connection`：优先驱动原生取消
   （psycopg/psycopg2 `cancel()`、sqlite3 `interrupt()`），没有原生取消的
   驱动退化为 `Connection.invalidate()`——关掉 DBAPI 连接，阻塞调用随即
   报错、连接不留在池里；
3. 取连接前、`conn.execute` 前、`fetchmany` 批次循环内都检查
   `cancellation_requested`；取消后抛 `NodeCancelledError`；
4. 正常完成/异常路径都在 `finally` 停看门狗并 `join(1.0)`，随后
   `engine.begin()` 照常 commit/rollback 归还连接。

修复后探针（`data/39-probe-sql-timeout.txt`，20M 行递归 CTE）：

```
[sql-timeout] flow raised NodeTimeoutError after 0.30s
[sql-timeout] +0.05s pool_checkedout=1
[sql-timeout] +0.20s pool_checkedout=0
[sql-timeout] +0.50s pool_checkedout=0
[sql-timeout] +1.00s pool_checkedout=0
```

对齐 r8 C1「SQL 上限异常后连接池归还正常」的正控：本次补的是**超时/取消
分支**——正常完成、上限异常、取消三条路径结束时 `checkedout` 都为 0。

回归覆盖：真 Flow 节点超时（`PT0.3S`）→ 2s 内 `checkedout==0`；预置
`cancel_requested` → 不建 engine/不取连接；直接调用中 `cancel_event` 置位
→ 查询 2s 内退出并归还；无取消源的旧执行桩结果形状不变。

## §6 边界与未覆盖

- 四通道业务码为本地 stub 复现，未对真实 Feishu/WeCom/Slack/DingTalk 服务端
  发消息；限流业务码取官方文档值，若各通道新增限流码需补表。
- SQL 取消在本地 SQLite（`interrupt()`）上验证；真实 PostgreSQL/MySQL 的
  `cancel()`/连接失效行为未在本轮环境复测，无原生取消的驱动走
  `invalidate()`（语义：连接不归还池，查询在服务端可能继续到语句结束）。
- 若连接池已被其它 run 占满，`engine.begin()` 的**取连接等待**仍不受
  `cancel_event` 约束（默认 `pool_timeout=30s`）；本轮修的是「本节点已持有
  连接后被超时遗弃」这一条，池耗尽的根因随首个超时连接回收而消除。
- 被引擎遗弃的节点线程在取消后抛出的中断异常由引擎丢弃（其结果不消费）；
  节点侧不再产生副作用或长期占用连接。
